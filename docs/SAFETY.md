# Safety Guidelines

SpaceKit removes files. That makes safety the most important property of the project, ahead of speed, features or convenience. This document is the contract: what SpaceKit will never do, how that's enforced, and what contributors must preserve.

> **The short version:** SpaceKit can never delete your disk, a volume, your home folder, your personal folders, system folders, credentials or repositories, and it never removes anything without showing you first. Automation is limited to what a rule recognises (regenerable data unless a job opts in to more) and folders you listed in the job, within a byte budget, and is journaled.

## 1. One gate for everything

Every removal, from every front end (the app, the TUI, the CLI and the background agent), passes through a single component: [`SafetyGuard`](../Sources/SpaceKitCore/Safety/SafetyGuard.swift). The `CleanupExecutor` asks the guard again **immediately before** touching each item, so a plan that was safe when it was reviewed is re-checked against the disk as it is at removal time. At that moment it also re-reads whether the item is or contains a git repository, and re-measures its size for the budget and the volume-share check. A check made before those facts are known (`clean` deciding whether a path is worth measuring, `jobs add` warning about a job's folders) asks `SafetyGuard.locationRefusal`, which judges the location alone. Size and repositories can only add reasons, so what it refuses stays refused whatever is there, and it never permits anything: the review and the removal judge the facts.

The guard judges a **removal target** ([`RemovalTarget`](../Sources/SpaceKitCore/Cleanup/RemovalTarget.swift)), never a bare path. One factory builds it once per item: the item's folder with every symlink resolved, the folder and the item pinned by device and inode, whether it is or contains a git repository, and its size. The guard reads those facts and no file itself, and it can't be asked without them, so no caller can skip the repository or volume-share checks by leaving a fact out. The same target goes to the Trash-or-delete decision and to the removal, so none of them resolves the path on its own.

The guard returns one of three decisions:

| Decision | Meaning |
|---|---|
| **allow** | May be removed. |
| **confirm** | May be removed only after a person explicitly acknowledges the shown warning. Never in automation. |
| **block** | Never removed, by anyone, in any mode. There is no override. |

**A cleanup a person starts runs only as a reviewed plan.** The executor has two inputs. A *reviewed plan* comes only from the review (`CleanupReview`), the one module behind the app's review sheet, the TUI's dialog and the CLI's preview: it drops blocked rows and rows the person unticked, and after the person's single acknowledgement for the whole plan it records exactly which reasons it showed for each row and, for each item, the location it judged: the path with the folder's symlinks resolved, and the folder and the item by device and inode. At removal time a reason outside that row's set skips the row: a warning on a row the review allowed outright, a repository that appeared, a folder that now holds a larger share of the disk than the review showed, or a block such as a volume mounted since. So does an item that is no longer at its reviewed location, because a folder above it now leads elsewhere or another item stands in its place: an accepted warning can't be carried to something the person never saw. A reviewed plan also records which executor made the review's verdicts, and it runs only on that executor. A context builds one executor per reading of the config, so after a settings change (a protected path added, `safety.trash: always`, a config file broken since) the context's new executor refuses a plan reviewed under the old settings: nothing runs and every row is skipped with "SpaceKit's settings changed after the review". The app's sheet then reviews the plan again in place; the TUI says "Nothing was removed: review it again", and the person opens the review again. A job run by hand or an approval completes with the executor current at that moment, never the one from when the job was evaluated. An *automatic plan* comes only from `JobRunner` for an automatic job; it acknowledges nothing, so anything that needs confirmation is skipped. No front end can mark a plan as confirmed on its own.

**What changes is what was checked.** After the guard's check, the removal ([`Remover`](../Sources/SpaceKitCore/Cleanup/Remover.swift)) opens the target's folder with no symlinks allowed in any component and refuses it unless the kernel's path for that handle is the folder the guard checked and its device and inode are the ones the target pinned. A folder swapped for a symlink, or moved away and replaced by another folder (even one holding a hard link to the same file), fails with nothing removed. The item itself must still have the pinned device and inode, so an item swapped for a symlink or another folder is refused too, and so is an item on a different volume than its folder. Deletion checks again at the handle it works through: a folder is opened by name and emptied only if that handle has the pinned device and inode, so a folder renamed into the item's place after the check is refused with nothing removed. A file or a link is unlinked as an entry, which can't remove a folder, so a folder swapped in for it stays. A file put in the item's place while the item is being emptied stays too: the item's contents are gone, and the run reports that it couldn't remove the item's name.

**Deletion never goes by path.** The item is removed by name relative to that handle. A folder is opened relative to its parent's handle without following symlinks, and its entries are removed by name. The removal keeps one folder open at a time, without recursion: it opens a subfolder by name, empties it, then climbs back through `..`, checks that it arrived in the folder it came from (same device and inode), and removes the emptied subfolder by name. If a folder was moved elsewhere during the removal, that check fails and the item stops with "… was moved while it was being removed; stopped there", instead of carrying on in the new parent. A subfolder swapped for a symlink during the removal is removed as a link, so the deletion never follows it out of the item. Because no step looks up a full path and only one folder is open at a time, neither the depth of the tree nor the open-file limit matters, and neither does losing search permission on a folder above.

**What can't be removed is left; everything else is removed.** An entry that can't be removed (an immutable file, say) stays, with the folders above it, and the removal carries on with the rest of the item. The item then fails with "Couldn't remove <first path>: <reason> (and N more)". What was deleted from an item that failed part way, for this reason or because a folder moved, is still written to the journal, charged to an automatic run's budget and counted in the bytes freed, and the failure says how much of it was deleted. A removal refused before anything went (the item changed since the check, is another volume, or its device can't be read) is a plain failure: nothing is measured, journaled or charged for it.

**A volume mounted inside an item stays.** The guard refuses mount points and folders containing them: an item holding a volume that is in the mount list is blocked as a whole, not removed around the volume, since a volume known up front is a sign the item isn't what a rule meant. A review checks against the mount list read when the config was loaded, and every run reads the list again before it removes anything. A volume mounted after that read is caught while deleting: every subfolder's device is compared with the item's, and a folder on another device is left alone, with the folders above it. The rest of the item is removed, and the report names what was left and why. A folder left for a volume doesn't count as an entry that couldn't be removed, and the bytes still on the volume aren't counted as freed. The app and the TUI scan the item's folder again instead of dropping it from their trees.

**The Trash keeps Put Back in cleanups you start.** Moving to the Trash goes through macOS's `FileManager.trashItem`, so Finder's Put Back works, and that call takes a path. So the folder and the item are checked against the target as above immediately before the move, and what arrived in the Trash is checked after it: it must have the target's device and inode. A swap in the moment between the check and the move is the one race that remains. It sends the wrong item to the Trash, where it can be put back, and the run reports it as a failure that says where it went instead of calling the item removed. A move macOS doesn't report a destination for can't be checked, so it is reported the same way, never as removed. FAT and exFAT volumes give an empty file a new inode when it moves; there, an empty file is accepted when an empty plain file arrived on the same volume, since nothing a swap could send instead holds any data. Every other item keeps the device-and-inode check.

**Automatic runs move to the Trash by handle.** Nobody watches an automatic run to put a wrong item back, so that race can't stay open there. An automatic run moves the entry out of the checked folder's handle straight into `~/.Trash`, opened as a handle too (a real folder of yours, created if missing), with `renameatx_np` and `RENAME_EXCL`: under the item's name, or `name 2`, `name 3` and so on, never over an existing entry. A folder above the item swapped for a symlink after the check can't redirect the move, because the folder handle stays the folder that was checked. What arrived is checked as above. Finder's Put Back doesn't know these entries; the journal records where each came from and where it went. An item on another volume than your home folder can't be moved this way, so an automatic run leaves it and reports it; clean it by hand.

**One place decides Trash or delete** (`Remover.method`): things already in the Trash are deleted, `safety.trash: always` and a plan's Trash setting trash everything else, and automatic runs trash anything that isn't 🟢 (see §4). The review asks the same decision for its Trash choice, its wording and the plan it hands the executor, and the app, the TUI and the CLI show that wording (`CleanupReview.disposalSummary`) instead of their own. A selection that mixes Trash entries with other items says which part goes to the Trash and which is deleted for good, and every front end marks wording that deletes anything permanently (`Disposal.isPermanent`) as a warning. The guard learns the outcome for its personal-folder rule.

## 2. Never: the whole disk, volumes and top-level folders

These are **blocked unconditionally** (`checkHardLimits`), regardless of configuration, confirmation or rules:

1. **The disk itself and every top-level folder:** `/`, `/System`, `/Users`, `/Applications`, `/Library`, `/private`, `/usr`, `/bin`, `/sbin`, `/etc`, `/var`, `/tmp`, `/opt`, `/Volumes`, `/cores`, `/dev`, and any path with fewer than two components.
2. **Volume roots and mount points:** `/Volumes/<anything>`, `/System/Volumes/<anything>` (Data, Preboot, VM, Update), any path that is a mount point, and **any folder that contains a mount point**. A volume mounted inside an item after this check is left alone when the item is deleted (see §1).
3. **Anything that contains a protected location.** Removing `~/Library` would remove `~/Library/Keychains`, so `~/Library` is blocked. The same ancestor rule makes the home folder, `/Users` and `/` impossible to remove.
4. **The home folder and its structure:** `~`, `~/Library`, `~/Library/Application Support`, `~/Library/Containers`, `~/Library/Group Containers`, `~/Library/Caches`, `~/Library/Developer`, `~/Library/Preferences`, `~/Library/Keychains`, `~/Library/Mail`, `~/Library/Messages`, `~/Library/Calendars`, `~/Library/Photos`, `~/Library/Mobile Documents` (iCloud Drive), `~/Library/CloudStorage`, `~/Documents`, `~/Desktop`, `~/Downloads`, `~/Pictures`, `~/Movies`, `~/Music`, `~/Public`, `~/Applications`, `~/Developer`, `~/.Trash`, `~/.config`, `~/.cache`, `~/.local`, `~/.docker`, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.kube`.
   *Things inside* folders like `~/Library/Caches` or `~/Downloads` can be removed (see the tiers below); the folders themselves cannot.
5. **Sealed trees, where neither the folder nor anything inside it is ever removed:** the operating system (`/System`, `/usr/bin`, `/usr/sbin`, `/usr/lib`, `/usr/libexec`, `/usr/share`, `/bin`, `/sbin`, `/private/etc`, `/private/var/db`), keychains, SSH/GPG/cloud credentials (`~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.kube`, `~/.config/gcloud`, `~/.config/gh`), Mail, Messages, Contacts, Calendars (including Calendar's group container), password managers (1Password, including 1Password 7, Bitwarden, Enpass, KeePassXC, Proton Pass, LastPass), and Docker Desktop's VM disk and group container (reclaim Docker space with Docker's own commands, never by deleting `Docker.raw`).
6. **Git metadata** (any path containing a `.git` component) and the **insides of library packages** such as `*.photoslibrary`, `*.musiclibrary` and keychains. Those are managed by their apps.
7. **Anything a `protected` rule describes** (databases, Docker volumes, photo libraries, credentials), and anything that contains it. For a rule whose path is a glob, that includes every folder a match could sit in, even before a match exists there.
8. **Your own protected paths** from `safety.protectedPaths`, plus their contents and ancestors, under the path as written and its location with symlinks resolved.
9. **Running as root.** SpaceKit refuses to remove anything, or run any tool command, when run with `sudo`.

**Spellings don't matter.** APFS treats `~/library`, `~/Library` and a differently normalized Unicode spelling as the same folder, so every comparison against these lists folds case and Unicode normalization (`PathUtil.comparisonKey`). On a case-sensitive volume this blocks more than strictly needed, never less. The guard checks each path as given, with symlinks in parent folders resolved, and (unless the item is itself a symlink) as it is spelled on disk. A home folder that is (or sits behind) a symlink is resolved once, and every home protection, built in, from a `protected` rule or from your config, applies under both its spellings.

Relative paths are refused, and so are `~name` paths: only `~` and `~/` are expanded. Paths are taken exactly as given, trailing spaces included, so `report ` is checked, measured and removed as `report `, never as `report`. `..` and symlinks in parent folders are resolved before checking, so a symlink can't smuggle a protected folder in under another name. Removing a symlink removes the link, never its target.

## 3. Tiers for everything else

| What | By hand (app, TUI, CLI) | Automatic jobs |
|---|---|---|
| 🟢 Rule item, `safe` (regenerable) | allow | allow, if inside the rule's locations |
| 🟡 Rule item, `review` | confirm | only if the job sets `includeReview: true`; moved to the Trash |
| 🔴 Rule item, `protected` | block | block |
| A git repository (`.git` directly inside) | confirm | block |
| Folder containing repositories | confirm (unless a 🟢 rule claims it) | block (unless a 🟢 rule claims it) |
| Personal data (Documents, Desktop, Downloads, Pictures, Movies, Music, iCloud, app containers) without a rule | confirm | only for a folder **listed in the job**, with `olderThan` ≥ 7 days **and** moving to the Trash |
| Anything no rule recognises | confirm | block, unless the folder is listed in the job; then moved to the Trash |
| A single item > 10% of the disk's used space | confirm | allowed up to 25%, blocked above |

"Inside the rule's locations" means under one of the rule's paths, or, for a pattern rule, a folder with a matching name under the rule's `roots` (or `scan.devRoots`) and outside its exclusions. Rule locations and job folders are resolved through symlinks, so this is judged on the item's location with symlinks in its parent folders resolved: `/tmp/x` counts as `/private/tmp/x`, and a symlinked parent that leads elsewhere takes the item out of scope. Every resolved spelling (including how the path is spelled on disk) must be inside, by hand and in automatic runs, and the same goes for folders listed in a job.

By hand, a rule speaks only inside its own locations. A name match elsewhere, such as a `node_modules` inside `~/.vscode/extensions`, counts as no rule: it needs confirmation like anything else no rule recognises. A `protected` rule blocks wherever it matches.

**Cleaning some rules gives each one what a full analysis would.** `clean <rule>`, `clean --safety`, `dev --rule` and jobs evaluate only some rules, and scan only those rules' locations. Every enabled rule and every `protected` rule still claims its share there, so a selected rule never gets anything another rule claims. That includes a job's own `paths:`: a `node_modules` inside a job folder stays unless the job lists the rule for it.

## 4. Automation limits

- **Never silently delete.** Jobs run in one of three modes: **observe** (notify only), **suggest** (prepare a plan and wait for approval) and **automatic**. New jobs default to *suggest*, except jobs created from 🟢 rules that remove files; a job created from a rule that runs a tool command starts as *suggest* whatever its policy says, since automatic runs skip most installed tools (§4).
- An automatic run has a budget of **`safety.maxBytesPerRun`** (default 100 GB). An item that would take the run over what's left of the budget is skipped and reported. The budget is charged with each item's size measured at removal time, not the size in the plan, including files that also have a hard link outside the item. The freed bytes in the result and the journal leave those files out, because their data stays on disk under the other link.
- **Automatic permanent deletion is allowed only for 🟢 regenerable items.** Every other item an automatic run removes goes to the Trash, even when the job says `action: delete`. That includes folders you listed in the job, which have no rule. Things already in the Trash can only be deleted, so an automatic run deletes them only when a 🟢 rule covers them, and skips them otherwise; the guard's verdict for an automatic run blocks them too, so `jobs show` neither lists them as allowed nor counts them in its `totalBytes`.
- **Every automatic run that removes something, or leaves an item or a tool command skipped or failed, posts a notification.** This happens even with `automation.notifications: false`; that setting only silences observe and suggest runs.
- Every removal is written to the journal (`spacekit journal`) as it happens.
- **Tool commands run unattended only from folders you can't change.** In an automatic run a tool command starts only when neither the program file nor any folder or symlink on the way to it is yours or writable by you (`CommandTrust.changeablePart`). Writable counts several ways, any one of them enough, so the check fails closed: your own access, write permission for the group or for everyone (sticky bit or not), or an access control list entry that lets anyone but root write, even when you yourself can't. Tools that pass are in `/usr/bin`, `/bin`, or a root-owned `/usr/local/bin` entry whose real file is root's too. A program in `~/.local/bin`, `~/go/bin`, `~/.cargo/bin` or a Homebrew prefix you own could be swapped by any program of yours for its own, which the agent would then start with Full Disk Access and nobody watching. The same goes for every program the tool starts by being a script: its `#!` interpreter, followed through `/usr/bin/env` to the program env finds, must be no more yours to change than the tool, so `npm` (`#!/usr/bin/env node`) runs unattended only when the `node` it starts is the system's too. Built-in rules' trusted tools get this check as well. The tool's `PATH` in an automatic run holds only the search folders you can't change. Only the folder is judged there, not each program in it (a link in `/usr/local/bin` can lead into an app in `/Applications`), so the program env looks up for a script is checked on its own, like the tool. A helper a tool starts by name isn't checked, and no built-in rule's command is known to start one: `xcrun`, which would search the `PATH` for a tool its developer folder lacks, runs unattended only when the developer folder has the tool (the Command Line Tools have no `simctl`). Such a command is skipped with "… can be replaced by any program of yours, so it runs only when you start it", and runs when you start the job or the cleanup by hand. On a typical Mac this skips `brew`, `docker`, `go`, `cargo` and the other Homebrew or per-user tools in automatic jobs. A command that cleans a whole rule (or removes a model) is also skipped in an automatic run when a folder below your home on the way to one of the rule's paths is a symlink (`CommandTrust.linkedPathRefusal`): the tool cleans that folder by its own lights, so `~/Library/Caches/go-build` linked to `~/Documents` would have `go clean -cache` clean your documents. By hand you review the command and start it yourself. A tool that does start gets settings SpaceKit chooses instead of yours, and a tool whose settings can't be left behind (`brew`, `pod`, `pnpm`, `bun`, `conda`) never runs automatically: see [Tool settings in automatic runs](#tool-settings-in-automatic-runs).
- **Confirmation is never implied.** Automatic runs acknowledge nothing, so anything that needs confirmation is skipped. When a person runs a job by hand (the app, the TUI, `spacekit jobs run --yes`), its plan goes through the same review as any other cleanup; the core never accepts a warning on their behalf.

### Tool commands

Rules can clean with the tool's own command (`docker builder prune`, `brew cleanup`, `xcrun simctl delete unavailable`) instead of removing files. Commands are held to the same standard as items:

- They run **without a shell**, with stdin from `/dev/null` and a 10-minute timeout. A tool still running then (or a child it left holding its output) gets SIGTERM, then SIGKILL, together with its process group.
- **With a cleaned environment.** A tool gets `PATH`, `HOME`, the user and locale variables, `TMPDIR`, `XDG_*`, Homebrew's settings (`HOMEBREW_*`, which decide what `brew cleanup` keeps) and the variables that move its own cache (`CARGO_HOME`, `GOMODCACHE`, `npm_config_cache` and the like; the full list is in [RULES.md](RULES.md#action)). A kept name that marks a credential (`TOKEN`, `PASSWORD`, `SECRET`, `KEY`, `AUTH` and similar, such as `HOMEBREW_GITHUB_API_TOKEN`) is dropped. Everything else stays behind: a variable can point a tool at another machine (`DOCKER_HOST`, `OLLAMA_HOST`), load code into it (`DYLD_*`, `NODE_OPTIONS`, and `DEVELOPER_DIR`, which picks the folder `xcrun` starts developer tools from) or hand it credentials (tokens, `SSH_AUTH_SOCK`). Every tool command SpaceKit starts gets this environment (`Shell.toolEnvironment`): rule commands and SpaceKit's own helpers alike (`launchctl`, `tmutil`, `osascript`, `open -R`). None of those helpers needs more, and one rule for every caller means no new caller can forget it. One program you start yourself gets your whole environment instead: the editor `spacekit config edit` opens (`$VISUAL` or `$EDITOR`), which needs it as any editor you start does. In an automatic run a tool gets less: only `PATH` (without the search folders you can change, see §4), `USER`, `LOGNAME`, `LANG` and `LC_*` from the environment, `HOME` set to SpaceKit's own home from the password database and `TMPDIR` to your temporary folder as the system names it (`confstr(_CS_DARWIN_USER_TEMP_DIR)`), never taken from the environment, since `HOME` decides where each tool's default cache is; plus the variables that leave its own settings files behind (`Shell.isolationVariables`, see [Tool settings in automatic runs](#tool-settings-in-automatic-runs)), and it starts in `/`, so no project settings in the folder SpaceKit started in reach it. Nobody watches that run, and any program running as you can set the agent's variables (`launchctl setenv`), so a tool home, an `XDG_*` folder or a Homebrew setting there could steer what the tool deletes (`GOMODCACHE` pointed at a folder of yours). The Docker questions below are asked in the same environment as the command.
- **Docker commands clean this Mac's Docker only.** Before a `docker` command, SpaceKit asks `docker context inspect` for the active context's endpoint, in the same cleaned environment the command gets, so the answer describes the Docker the command will use (`DOCKER_HOST`, `DOCKER_CONTEXT` and `BUILDX_BUILDER` never reach it). Unless the endpoint is a unix socket (Docker Desktop, OrbStack, Colima), the command is skipped with that reason. `docker builder` acts on the selected buildx builder, which can be remote while the context is local (`docker buildx create --driver remote … --use`, Docker Build Cloud), so for `docker builder` and `docker buildx` commands SpaceKit also asks about the selected builder: it must use the `docker` or `docker-container` driver, and each node must be a unix socket or a context whose endpoint is one. The builder is read from `docker buildx ls --format json`, or, from a buildx older than 0.13 that can't print JSON, from the `Driver:` and `Endpoint:` lines of `docker buildx inspect`. Without the buildx plugin (`docker buildx version` answers that `buildx` isn't a docker command, as with Colima and Homebrew's `docker`), `docker builder` is the classic builder, which prunes the build cache of the active context's daemon, so the context check is enough. Answers are read from standard output only, so a warning on standard error neither passes for an answer nor refuses one; a failed query, a timeout or output that doesn't parse skips the command (`CommandTrust.dockerRefusal`). The one thing read from standard error is the line the docker binary itself prints when the buildx plugin is missing, `docker: 'buildx' is not a docker command.` (or Docker 28's `docker: unknown command: docker buildx`), taken only as a whole line and only when `docker buildx version` failed.
- **The executable must be a bare name** such as `brew`: no `/`, no `..`, no `{name}` placeholder. Anything else is rejected when the rule is validated and again before it runs. The name is looked up in `PATH` plus the usual Homebrew, Cargo, Go, Bun, Docker and OrbStack locations, and relative `PATH` entries are ignored. The folder it is found in is resolved to its real location, but the executable keeps the name it was asked for. Multi-call tools such as rustup's proxies (`cargo` → `rustup`), mise shims and `bunx` decide what to do from the name they are run under, so resolving the name too would run a different program.
- **Built-in trust covers built-in rules only.** Rules from SpaceKit's own rule library may run the executables on the built-in trusted list (see [RULES.md](RULES.md#action)). A rule from any rule folder runs a command only if its executable is in your `safety.allowedCommands`, whatever the trusted list says. A rule file you download can't run programs you haven't named. The built-in library is compiled into the binary from the repository's `rules/` (`BuiltinRules.embedded`), so being built-in is a fact of the build: no folder beside an installed binary or in the app bundle is read for it. Only debug builds read `$SPACEKIT_RULES_DIR` instead; release builds ignore it, so no environment variable can grant built-in trust. One module, `CommandTrust`, decides from the rule's origin, the kind of run and this executable policy whether a command runs, and rule validation asks it too.
- **Unattended, only from folders you can't change, and with settings SpaceKit chooses.** See §4: an automatic run skips a tool whose file, script interpreter, or a folder or symlink on the way to them, you own or can write; and see [Tool settings in automatic runs](#tool-settings-in-automatic-runs) below.
- **Your own rules' commands run by hand only, and only once you accept them.** The background agent runs as you, with the Full Disk Access the docs ask you to grant, and any program running as you can write a rule file, and the config file too. So in an automatic run a command from a rule outside the built-in library is refused, even when its executable is in `safety.allowedCommands`. In a cleanup you start yourself, such a command is always a warning, never allowed outright: the review shows every argument (control characters made visible) and the file the tool was found at, with the file it really is when that's a symlink (`CommandTrust.ownRuleWarning`). `--yes` alone skips it as not accepted; it runs only with `--accept-warnings`, a yes on the terminal, or the app's and the TUI's acknowledgement. The run starts the program the review named: a tool found at another place by then (a program put earlier on the search path) is skipped as changed since the review. `safety.allowedCommands` and the launcher names below are a backstop that catches mistakes; your acknowledgement is the barrier, since plenty of ordinary tools run code their arguments give them (`brew sh`, `npm exec`, `go run`, an editor's `-c`).
- **No shells or interpreters in `allowedCommands`** (a backstop, see above). A program that runs whatever code its arguments give it (`sh`, `bash`, `zsh`, `python…`, `perl`, `ruby`, `node`, `osascript`, `swift`, `awk`, `sqlite3`) or starts another program (`env`, `xargs`, `find`, `open`, `nohup`, `nice`, `time`, `sudo`, `xcrun`, `make`, `git`, `ssh`, `rsync` and the like) would turn one allowed name into "run anything". Listing one makes the config invalid, so cleaning stops until it's removed (see §5), and the executor refuses such a name for non-built-in rules even if it is handed one directly. The checks come in layers: an allowed name must be plain ASCII (letters, digits, `.`, `_`, `+`, `-`), because APFS folds case fully and `/bin/baſh` starts bash; names are compared with full Unicode case folding; and when an allowed tool's command is reviewed, and again right before it starts, the file it was found at is checked (`CommandTrust.launcherIdentityRefusal`): the last component of its real path must pass the same name rules, so a symlink called `cleanup-tool` that leads to `/bin/sh` is refused, and a script's `#!` interpreter must be no launcher either, followed through `/usr/bin/env` and its options to the program it starts (`#!/usr/bin/env python3` is refused, and so is a script whose interpreter SpaceKit can't tell). Files aren't compared with each other: the Command Line Tools install one shim file as `git`, `pip3`, `swiftc` and dozens more, and Volta and mise link every tool to one shim, each running what the name it was started as says. So a copy or hard link of a launcher under another name isn't caught by its file; it is left to your review, which names the path the program was found at. Built-in rules' trusted tools skip this name check: their names are fixed in the binary, and some, such as `npm`, are scripts that `node` runs. (In automatic runs their interpreters are still checked, see §4.) A `#!` line is read the way the macOS kernel reads it: within the first 512 bytes, up to a newline or `#`, the interpreter up to the first space or tab and the rest split at spaces and tabs into one argument per word, as `man env` describes for Darwin (a carriage return is part of a word), and env's options are read from those words as macOS's `env` reads them (`-i`, `-u`, `-v`, `-0`, `-S`). A line the kernel wouldn't run, an `env` other than `/usr/bin/env`, `env -P` or `-C`, options macOS's `env` doesn't have, quotes, escapes or `${…}` in `env -S`, and a file that is neither a Mach-O program nor a `#!` script (which env would run with `/bin/sh`) are refused, since SpaceKit can't tell which program would start. The full list is in [CONFIGURATION.md](CONFIGURATION.md#values).
- **The same gates as items:** refused when running as root, refused while the config is invalid (see §5), refused when the rule is `protected`, need confirmation by hand when the rule is `review`, and run automatically only for 🟢 rules or with `includeReview`. In an automatic run, a command whose estimated size exceeds what's left of the budget doesn't start, and what it actually freed is charged afterwards.
- **Per-item commands are checked like the item.** For an `itemCommand`, the item substituted for `{path}` and `{name}` goes through the guard like any other item and must be permitted. A reviewed per-item command runs only while that item is at the location the review judged it at, like a reviewed item; otherwise it is skipped as changed since the review. A `{name}` or model name that starts with `-` is refused, since the tool would read it as an option.
- **A command runs only as its rule says now.** A planned command runs only if its rule is still loaded and still produces the same arguments. If the rule was disabled, removed or became invalid, or its command changed since the plan was made, the command is refused and the plan must be refreshed. An older suggestion therefore asks for a refresh instead of running a command its rule no longer gives.
- **AI models can be removed by their tool.** An `ai` rule may set `ai.removeCommand` (for example `ollama rm {name}`) for tools whose models share files. It goes through the same checks as `action.command`. See [RULES.md](RULES.md).

### Tool settings in automatic runs

A tool reads settings of yours besides its arguments: files in your home folder, in the folder it starts in, and variables. Any program running as you can write those files, so in an automatic run, where nobody watches and the tool has SpaceKit's Full Disk Access, they could decide what it deletes (a cache folder pointed at your documents) or which code it runs (a plugin, a downloaded toolchain). In an automatic run a tool therefore starts in `/` (no `go.mod`, `.npmrc`, `uv.toml` or `deno.json` of a project), and gets variables that leave its settings files behind (`Shell.isolationVariables`). A built-in rule's tool runs unattended only when that is enough (`CommandTrust.isolatedTools`); the tools whose settings can't be left behind, and any tool not in this table, run only when you start them (`CommandTrust.unisolatedTools`). A test fails when a built-in rule uses a tool missing from both lists (it checks those lists, not this table). "Runs" below also needs the tool, its interpreters and the folders on the way to them to be ones you can't change (§4), which typical installs aren't: Homebrew's `go`, `deno`, `uv` and `ollama` under a prefix you own, `docker` and `ollama` linked into apps in `/Applications` (which the admin group can write), `rustup` in `~/.cargo/bin`, and `xcrun` with Xcode in `/Applications` or with only the Command Line Tools (no `simctl`) are all skipped unattended. That is why a job SpaceKit suggests for a rule that runs a command starts as a suggestion (`Job.suggested`): you approve it and it runs by hand.

| Tool | Built-in commands | Settings of yours it reads | In an automatic run (runs unattended only when found in a folder you can't change) |
|---|---|---|---|
| `go` | `go clean -cache`, `go clean -modcache` | Go's env file (`~/Library/Application Support/go/env`: `GOMODCACHE`, `GOFLAGS`, `GOTOOLCHAIN`); a `go.mod` or `go.work` in the folder it starts in, whose `toolchain` line can make it download and start another Go | Runs, with `GOENV=off`, `GOTOOLCHAIN=local` and no `GOFLAGS` |
| `npm` | `npm cache clean --force` | `~/.npmrc` and the global npmrc (`cache=` decides what it deletes); a project's `.npmrc` | Runs, with `NPM_CONFIG_USERCONFIG` and `NPM_CONFIG_GLOBALCONFIG` set to `/dev/null`; the `node` its `#!` line starts is checked like the tool |
| `uv` | `uv cache clean` | `uv.toml` in `~/.config/uv` or a project (`cache-dir` decides what it deletes) | Runs, with `UV_NO_CONFIG=1` |
| `deno` | `deno clean` | `DENO_DIR` (not passed), which decides what it deletes; no settings file outside a project | Runs |
| `rustup` | `rustup toolchain uninstall {name}` | `RUSTUP_HOME` (not passed); `~/.rustup/settings.toml`, which doesn't move what it uninstalls | Runs |
| `ollama` | `ollama rm {name}` | none: it asks the Ollama server on this Mac (`OLLAMA_HOST` isn't passed), which removes the model | Runs |
| `docker` | `docker builder prune --force`, `docker image prune --all --force` | `~/.docker`: contexts, plugins in `cli-plugins` and `cliPluginsExtraDirs`, credential helpers | Runs, with `DOCKER_CONFIG=/var/empty`, an empty folder only root can change: the default context (`/var/run/docker.sock`, which Docker Desktop and OrbStack can link to their own socket; a Colima context isn't used) and no plugins of yours. `/var/empty` and Docker's system plugin folders (`/usr/local/lib/docker/cli-plugins` and the like), with every plugin in them, must be ones you can't change |
| `xcrun` | `xcrun simctl delete unavailable`, `xcrun simctl runtime delete unavailable` | `DEVELOPER_DIR`, `SDKROOT`, `TOOLCHAINS` (not passed); its lookup cache in your temporary folder | Runs, with `xcrun_nocache=1`, when the developer folder `xcode-select` chose (`/var/db/xcode_select_link/usr/bin`) is one you can't change and has `simctl`; otherwise xcrun would look for it on the `PATH`. A missing link, Xcode in `/Applications` (which the admin group can write) and the Command Line Tools alone don't pass |
| `brew` | `brew cleanup`, `brew cleanup --prune=all` | `~/.homebrew/brew.env` (`HOMEBREW_*` settings such as what cleanup keeps and where its cache is); formula code from taps in folders you own | Refused |
| `pod` | `pod cache clean --all`, `pod repo remove {name}` | `~/.cocoapods/config.yaml` (cache and repos folders); `~/.gemrc` and gems in `~/.gem`, which Ruby loads | Refused |
| `pnpm` | `pnpm store prune` | `store-dir` in `~/.npmrc` or pnpm's own rc file | Refused |
| `bun` | `bun pm cache rm` | `install.cache.dir` in `~/.bunfig.toml` | Refused |
| `conda` | `conda clean --all --yes` | `pkgs_dirs` in `~/.condarc`; Python's packages in your home folder | Refused |
| any other | | not checked | Refused |

Each refusal says why, ending in "so '<tool>' runs only when you start it"; started by hand, the tool runs with your own settings, as you'd run it yourself. The checks cover the tool's file, its interpreters and the folders on the way to them, not every file the tool loads from its own installation (npm's JavaScript, Go's `GOROOT`).

## 5. Defaults that favour you

- **Preview first.** The CLI previews by default (`--yes` to act), the TUI and app always show a review screen listing every item with the guard's verdict and every reason it gave, each marked with the decision it calls for on its own. `--yes` alone runs only what the guard allows outright; a warning is accepted only by `--accept-warnings` next to it, or by answering the question on a terminal, in both cases after the preview printed it. A row whose warnings weren't accepted is skipped as "Warnings not accepted", listed in the result (always present in `--json` output with `--yes`) and counted as a problem, so the command exits with status 1, whether it is an item or a tool command. The TUI wraps long lines to the dialog and accepts `y` only after every line has been on screen; jumping to the end with End doesn't count the lines skipped. The app needs a ticked acknowledgement before it removes anything with a warning.
- **The Trash by default.** `safety.trash: always` is the default, so everything can be put back until you empty the Trash. With it, the CLI refuses `--permanent` and the app hides the delete option. Set `safety.trash: rules` to let regenerable caches be deleted directly.
- **A broken config stops cleaning.** If the config file exists but can't be read (including a symlink to a missing file, or a file other users can change; see [CONFIGURATION.md](CONFIGURATION.md#invalid-config)), read-only features keep working with the defaults and a warning, but every removal and tool command, manual or automatic, is refused with "Config file is invalid: … Fix it (spacekit config validate) before cleaning." The defaults would lack your protected paths, allowed commands and disabled rules, so they are never used to clean. The TUI's header and a banner in the app's main window say so for as long as the problem lasts.
- **Built-in protections can't go missing.** The built-in rules are compiled in, and the test suite fails when any of them doesn't parse or has an error, so a protected rule such as `credentials.registries` (`~/.npmrc`, `~/.docker/config.json`) can't be dropped by a broken or missing file at run time.
- **Only valid rules are loaded.** A rule with a validation error is reported (`spacekit rules validate`) and not loaded. A rule in your folder can't take the place of a built-in `protected` rule, and a rule of yours with a built-in rule's id may only narrow it: keep its paths within the built-in ones, add exclusions, raise thresholds, ages or the safety level, run its jobs less often. One that adds a path, a pattern or a command, lowers anything or schedules its jobs more often is rejected and the built-in rule stays, so a rule file can't widen what an existing automatic job removes. The engine checks an override's paths again each time it resolves them for an analysis, and the guard and the rule index each time they ask whether the rule covers a path (`Rule.checkedPaths`, used by `RuleEngine.checkedOverride` and `RuleScope`), since a symlinked folder can be pointed elsewhere after the rules load; a path that now leads outside the built-in rule is left out, with an error in the analysis (`Analysis.ruleIssues`) and the agent's log, and the guard treats an item there as one no rule covers. The agent's log names the rules of yours it uses in place of built-in ones. `rules.disabled` never turns off a `protected` rule. See [RULES.md](RULES.md#your-own-rules-and-overrides).
- **Only what you reviewed.** A confirmation covers only the warnings the preview showed, for the item at the location the preview judged. If the check at removal time raises a reason the preview didn't have for that row (a warning on an item it allowed outright, a repository that appeared, a larger share of the disk than the preview showed, a block), or the item is no longer at its reviewed location (a folder above it leads elsewhere now, or something else stands in its place), the item is skipped with "Changed since you reviewed it: …", listed with the run's result, and the run reports a problem (the CLI exits with status 1). A share of the disk at or below the one shown is the same warning. A run reads the disk's capacity once, when it starts, and judges every item's share against that reading, so removing one item (which shrinks the used space) doesn't make the next one a larger share than the review showed. Every item in a plan records when the scan it came from started. Plain files directly in a folder ("Files in …" items) and entries in the Trash that were modified, created or moved there after that time weren't in the preview, so they are left alone. Each item is checked against its own scan, so a plan that mixes scans (the app's cleanup list outlives a rescan) never uses a later scan's time for an earlier scan's items. A "Files in …" item removes only the files it counted, never a file another rule claims in the same folder. The review judges those files as a whole; the run checks each one again on its own, and a file that check refuses (a protected path, say) stays and is reported with its reason, never dropped quietly. Since the review couldn't have shown a reason that belongs to one file, such a file is left like a refused item, not as a change since the review, so it isn't a problem and the run doesn't fail over it: it is the item's skip reason when nothing else went, otherwise a note in the result (`notes` in `--json`). The same goes for files past an automatic run's budget. An item saved without its scan time (an old suggestion) or a "Files in …" item saved without its file names can't remove loose files or Trash entries; refresh it. Removing an AI model stored as a cache removes the model's own entries, never the folder around them. Approving a suggestion evaluates its job again first and drops items that no longer meet the job's conditions. What runs is described by that evaluation, not by the saved suggestion, which other programs running as you could edit: the saved file can only narrow it (fewer loose files, an earlier scan start, a repository it recorded), never add a file, a later scan start or another rule.
- **Read-only scanning.** Scans read names, sizes and dates, and never read the contents of your files. The exceptions are small metadata files: Ollama's model manifests (JSON lists of the blobs each model uses, read to size models), the system's `/usr/share/firmlinks`, and SpaceKit's own config, rules and state. SpaceKit sends nothing anywhere.
- **Names can't rewrite the screen.** The CLI and TUI pass file names, paths, rule text and tool output through one sanitizer, `TerminalText.sanitize`, which shows control characters as visible escapes. A file named with an escape sequence can't hide or rewrite a line of a cleanup preview.
- **Journal.** `~/Library/Application Support/SpaceKit/journal.jsonl` records what was removed, when, how (`trash`, `delete` or `command`), by which rule or job, and where trashed items went. It is written one entry per removal as each happens, so an interrupted run still leaves a record, and each loose file gets its own entry. Quitting doesn't cut a cleanup short: the app and the TUI wait for a running cleanup, and the TUI holds SIGTERM, SIGHUP and SIGINT until it finishes, then exits. Deleting something already in the Trash is recorded as `delete`. A journal write that fails is reported with the run's result (and the CLI exits nonzero), never swallowed.

## 6. For contributors

- **The guard is the only gate.** New features that remove anything must go through `CleanupExecutor` (which calls the guard), and anything a person starts through `CleanupReview` first: a reviewed plan is the only manual input the executor takes. The executor's own files in `Cleanup/` do the removing. `SafeRemoval`, which performs the handle-based removal described in §1, is module-internal and called only from the removal module in `Cleanup/`: `CleanupExecutor`'s files, `Remover` and `RemovalTarget`. Never call `FileManager.removeItem`, `trashItem`, `removefile`, `unlinkat` or `rm` anywhere else. The only exceptions are SpaceKit's own files: the temporary file `LockedFile.write` made next to one of SpaceKit's files when writing it fails, the LaunchAgent plist on `spacekit agent uninstall` (`LaunchAgent.uninstall`), and the `request` file in `SPACEKIT_DEBUG_DIR` once a debug build has read it (`DebugAutomation`). Tests remove their own `TempTree` folders.
- **Config can add protections, never remove them.** Don't add options that weaken the lists above.
- **`SPACEKIT_HOME` is for debug builds only.** It points the guard's idea of home at a sandbox, which would strip every home protection from the real home, so release builds ignore it (`PathUtil.home`).
- **`SPACEKIT_RULES_DIR` is for debug builds only.** It replaces the embedded rules with a folder's, for trying rule edits without rebuilding. Rules in that folder get built-in trust, so release builds ignore it (`BuiltinRules.standard`). A folder that is missing or holds no rules would take the protected rules with it, so then the embedded rules stay and the rule library reports an error (`spacekit doctor`, `spacekit rules validate`).
- **Print untrusted text through `TerminalText.sanitize`.** That includes anything from the disk, a rule file or a tool's output that reaches a terminal.
- **Every guarantee has a test.** A change that makes any of them fail does not ship. Add a test for any new rule you introduce.
  - [`SafetyGuardTests`](../Tests/SpaceKitCoreTests/SafetyGuardTests.swift): the whole-disk, home, sealed-tree, repository, personal-folder, mount-point, symlink, root, `~name`, case and Unicode, protected-rule and volume-share rules, and the automation tiers.
  - [`CleanupReviewTests`](../Tests/SpaceKitCoreTests/CleanupReviewTests.swift): nothing that needs confirmation runs without acknowledgement, a warning the review didn't show for a row is refused (also on a row it allowed outright, and a share of the disk larger than the one shown, while a run takes every share from the capacity it read when it started), an accepted warning holds only at the reviewed location, a reviewed plan runs only on the executor that made its review, unticked and blocked rows never reach the executor, and the review's totals and Trash wording.
  - [`CleanupExecutionTests`](../Tests/SpaceKitCoreTests/CleanupExecutionTests.swift): automatic runs trashing instead of deleting, items already in the Trash, the budget charged with measured sizes, repositories re-checked at removal time, the journal written per removal, each item's scan start time, warnings that are new at removal time, hard-linked files in freed bytes, the invalid-config refusal, symlinks and handle-based removal.
  - [`RemovalTests`](../Tests/SpaceKitCoreTests/RemovalTests.swift) and [`SafeRemovalTests`](../Tests/SpaceKitCoreTests/SafeRemovalTests.swift): one removal target per item; an item or folder swapped after the check refused, by delete and by Trash, including a folder renamed into the item's place after the entry check and a file swapped for a folder; a file put in the item's place while it is emptied left; a volume mounted inside an item left and reported (a test can't mount one, so it stands one in through the executor's `device` seam); an automatic run's Trash move by handle (a parent swapped for a symlink before the move doesn't redirect it, entries in the Trash are never overwritten, an item on another volume is left), the Trash move checked after it (also without a reported destination, and for an empty file on a volume without stable inodes, stood in through the executor's `keepsInodes` seam); the one Trash-or-delete decision; a symlinked home protected at its real location, including `protected` rules' paths; a subfolder swapped for a symlink mid-removal, a folder moved out from above the walk, trees deeper than `PATH_MAX` and the open-file limit, a deep tree on a small stack, an entry that can't be removed (also next to a mounted volume), and a folder above without search permission.
  - [`PartialRemovalTests`](../Tests/SpaceKitCoreTests/PartialRemovalTests.swift): an item deleted only in part is reported, journaled and charged to the budget for what went.
  - [`SubsetEvaluationTests`](../Tests/SpaceKitCoreTests/SubsetEvaluationTests.swift): a rule or job evaluated on its own never gets what another rule claims.
  - [`CleanupCommandTests`](../Tests/SpaceKitCoreTests/CleanupCommandTests.swift): bare names, built-in trust and `allowedCommands`, your own rules' commands refused in automatic runs, code launchers refused, the root, config, budget and per-item gates for tool commands, and the command timeout.
  - [`CommandTrustTests`](../Tests/SpaceKitCoreTests/CommandTrustTests.swift): the trust decision for each origin, run and executable (launchers in any spelling APFS resolves, behind a symlink, and as the interpreter of a script, directly or through `env`; tools sharing a launcher's shim file still run), every command of your own rules needing acknowledgement with its full arguments and resolved path shown, the program bound to where the review found it and a per-item command to the item's reviewed location, the cleaned environment (smaller in automatic runs), refused commands never reaching the process runner, budget charging and names that start with `-`. [`AutomaticToolTests`](../Tests/SpaceKitCoreTests/AutomaticToolTests.swift) add the automatic run's checks: what makes a file or folder changeable (group, everyone, an access control list, a symlinked folder), the PATH without your folders, script interpreters of trusted tools, the isolation variables and working folder, and every built-in rule's tool isolated or refused. [`ProgramHeaderTests`](../Tests/SpaceKitCoreTests/ProgramHeaderTests.swift): `#!` lines read as the kernel reads them, and `env`'s one argument as macOS's `env` reads it. They run through the executor's `runner` seam with a recording runner, so no real tool starts.
  - [`DockerEndpointTests`](../Tests/SpaceKitCoreTests/DockerEndpointTests.swift): the local Docker check: remote contexts, remote, cloud and Kubernetes buildx builders, builder nodes through contexts, Docker without the buildx plugin, a buildx too old to list as JSON read from `docker buildx inspect`, and failed, timed-out, malformed or noisy answers, all scripted through the recording runner.
  - [`RuleLoadingTests`](../Tests/SpaceKitCoreTests/RuleLoadingTests.swift): overrides that may only narrow built-in rules (checked again where the engine looks, in [`OverrideRecheckTests`](../Tests/SpaceKitCoreTests/OverrideRecheckTests.swift)), protected rules that can't be disabled, invalid rules that aren't loaded, every embedded rule valid and identical to `rules/`, credentials protected with no rules folder on disk, and `SPACEKIT_RULES_DIR` read by debug builds only.
  - [`AutomationTests`](../Tests/SpaceKitCoreTests/AutomationTests.swift): no confirmation on a person's behalf, notifications from automatic runs, and the agent's log naming your replacements of built-in rules.
  - [`ConfigValueTests`](../Tests/SpaceKitCoreTests/ConfigValueTests.swift) and [`ConfigUpdateTests`](../Tests/SpaceKitCoreTests/ConfigUpdateTests.swift): strict ages and schedules, code launchers and names that aren't plain ASCII in `allowedCommands` making the config invalid, a config that doesn't parse is never overwritten, and config symlinks.
  - [`ContextUpdateTests`](../Tests/SpaceKitCoreTests/ContextUpdateTests.swift): config changes decide validity from the file as it is at that moment (a fixed file adopted, an invalid one refused and left as it is), and every run reads the mount table again.
  - [`FileTrustTests`](../Tests/SpaceKitCoreTests/FileTrustTests.swift): config and rule files other users can change (by mode or access control list) aren't read, built-in rules that no file owner can refuse, and SpaceKit's own files written with fixed modes whatever the umask.
  - [`PathUtilTests`](../Tests/SpaceKitCoreTests/PathUtilTests.swift) and [`TerminalTextTests`](../Tests/SpaceKitCoreTests/TerminalTextTests.swift): `SPACEKIT_HOME` ignored unless the build allows it, comparison keys, and the terminal sanitizer.
- **Rules must be honest.** If removing something costs a 20 GB download, it's `review`, even if it's "just a cache". See [RULES.md](RULES.md).
- **Debug hooks stay sandboxed.** The app's `SPACEKIT_DEBUG_DIR` automation (debug builds only) can only run cleanups whose every item lies inside a temporary sandbox home, never runs tool commands, and never confirms warnings, so it removes only items the guard allows outright. It deletes those items instead of moving them to the Trash, because the Trash is the real one outside the sandbox, and it refuses to run while the config sets `safety.trash: always`. A `snapshot=` value must be a bare file name inside the debug folder.

## Reporting a safety problem

If you find a way to make SpaceKit remove something it shouldn't, please report it privately to the maintainers rather than in a public issue, with the path, the command or steps, and `spacekit doctor` output.
